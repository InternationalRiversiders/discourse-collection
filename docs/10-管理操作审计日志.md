# 管理操作审计日志（非公共 API）

**目的与归属**：对专辑的「管理操作」留痕——admin（及经 `collection_moderators_can_manage_collections` 获得管理权的 moderator）对专辑 **名称 / 简介 / topic 备注 / owner / 邀请行** 的改动。**判定一律看操作者是否动用了 staff 权限**：staff 对**自己在该专辑没有对应角色**的专辑所做的前述改动即记（含他人专辑与无主专辑）——反之，操作者若本就以自己在该辑的 **owner / 共同维护者** 身份在做**凭该身份本就能做**的事（改自己专辑的名 / 简介 / note），属常规编辑、**不记**（staff 与非 staff 同口径）。「凭角色即可」的边界逐型不同：改名 / 改简介只认 **owner**（05 的 1；共同维护者本无此权），改 topic 备注认 **owner 与共同维护者**（04 的 4）。改 owner 一型不适用本判定，仍按发起者身份（见本节 1 表）。**另行判定的 = `collection_invite_revoke`**：它按「是否**代撤他人**发起」判定——管理型 staff 撤销**自己发起**的邀请不记（那是处置自己的东西，不是管理动作），撤销他人发起的才记。日志**不是公共 API**：不建插件表、不加站点设置、无插件查看端点；落核心 `user_histories`，**仅在 admin「管理 → 日志 → 员工操作日志」页可浏览**（moderator 不可见，见本节 3），经「全表浏览 → 逐行钻取 / subject 点筛 / URL queryParam」定位。

**写入时机**：管理操作**成功事务后**补记（照通知入队模式；事务失败不记）。「改 owner」恒走邀请制（05 的 2）——换主本身已有 `collection_invites` 留痕，故本日志在**受邀人接受、owner 实际落定**（05 的 2.5 `type=1`）时补记，**不在发起时记**。**唯一既是发起又是落定的是 staff 自邀接管**（05 的 2.7）：它在发起请求的事务后补记（无需等任何人接受）。「撤销邀请」（05 的 2.2）同样在撤销成功的事务后补记——注意**该事务会把被撤行物理删掉**，故**记日志所需的值必须在删行之前取出**：发起者用户名（`target_user_id` / `type=0` 的 `details`）、受邀人用户名（`type=1` 的 `details`）、`action_type`、专辑名（`context`），以及 `type=1` 所需的**撤销时刻现任 owner 用户名**（`details` 旧主一侧，须现查 `collection_teamworkers`）。

## 1. custom_type 与写入形态

5 个 custom_type，action 一律 core `UserHistory.actions[:custom_staff]`（= 23）。数值勿自增、勿占 `UserHistory.actions` 的 int 段。

| custom_type | 触发 | 写入的值（列见本节 2） |
| -- | -- | -- |
| `collection_name_change` | staff 改名（05 的 1），且操作者**不是该辑 owner** | `previous_value` → `new_value`：旧名 → 新名 |
| `collection_intro_change` | staff 改简介（05 的 1），且操作者**不是该辑 owner** | `previous_value` → `new_value`：旧简介 → 新简介 |
| `collection_topic_note_change` | staff 改写 topic 备注（06 的 1），且操作者**既非该辑 owner 也非其共同维护者** | `previous_value` → `new_value`：旧 note → 新 note（`null` 清空即 旧 → 空） |
| `collection_owner_change` | staff 发起的换主（`type=1`）接受落定（含无主专辑指定首任）、**staff 自邀接管**（05 的 2.7，当场落定）；owner 自主转让不记 | `previous_value` → `new_value`：旧 owner → 新 owner（无主专辑则前值为空）；自邀接管的新主即操作者本人 |
| `collection_invite_revoke` | 管理型 staff 撤销**他人发起**的未决邀请（05 的 2.2；**撤销自己发起的不记**） | 只写 **`details`**（`previous_value` / `new_value` 恒空），记被撤的那次邀请「本来要做什么」——换主邀请（`type=1`）：`<现任 owner 用户名> → <受邀人用户名>`；加维护者邀请（`type=0`）：`<发起者用户名> + <受邀人用户名>`。符号即语义：`→` = 换主方向、`+` = 加人；两端都是用户名字面，故与界面语言无关。槽位取不到用户时（账号已注销 / 无现任 owner）记 **`❌`** |

**第 5 型的写入形态**（逐字段；照 `Collection::OwnershipTransfer#record_owner_change_if_staff_initiated` 的直写式样）：

```ruby
UserHistory.create!(
  action:         UserHistory.actions[:custom_staff],  # 23
  custom_type:    "collection_invite_revoke",
  acting_user_id: guardian.user.id,                    # 撤销者本人（管理型 staff）
  target_user_id: invite.inviter_user_id,              # 发起该次邀请的人（已注销则 nil）
  subject:        "Collection (#{invite.collection_id})",
  context:        invite.collection.name,              # 撤销时刻的专辑名快照
  details:        <按下表拼>,
)
```

| 被撤的邀请 | `details` |
| -- | -- |
| `type=1`（换主） | `"<现任 owner 用户名> → <受邀人用户名>"`——如 `devstaff → alice` |
| `type=0`（加维护者） | `"<发起者用户名> + <受邀人用户名>"`——如 `bob + alice` |
| 槽位取不到用户 | `❌` 顶替该侧——如 `❌ → alice`、`bob + ❌` |

- 「现任 owner」取**撤销时刻**的实时值（`CollectionTeamworker` 里 `is_owner=true` 的那行）；「发起者」= `invite.inviter`，「受邀人」= `invite.invitee`。**注意 `inviter_user_id` / `invitee_user_id` 均为 `ON DELETE SET NULL`**，故两处都可能是 nil → 该侧落 `❌`；无主专辑的 `type=1` 邀请「旧主」一侧天然无人，同样落 `❌`。

- `details` 是**纯数据、不经翻译**（admin 页对该列只 `escapeExpression` 直出）。这正是选它而非 `previous_value` 承载用户名的原因：既不随写入者语言漂移，也无需为多语言改 core。

## 2. 字段布局（核心 `user_histories` 列）

| 列 | 内容 |
| -- | -- |
| `action` | `custom_staff`（= 23） |
| `custom_type` | 本节 1 表 5 值之一；staff-action-log 下拉细分的**精确过滤键** |
| `subject` | 稳定令牌 `Collection (id)`，列显 `Collection (42)`；同一专辑全部管理动作经此聚合，命中 core `(subject, id)` 索引 |
| `context` | **写入时刻的专辑名快照**（改名只影响新行，旧行保留旧名，行内可读） |
| `previous_value` / `new_value` | 被改字段的前后值（见本节 1）。**前四型专用**；`collection_invite_revoke` 两列恒空 |
| `details` | **仅 `collection_invite_revoke` 使用**（见本节 1），存被撤邀请的符号式描述。该列在 admin 页**不经翻译**（短文本在 details 列内联、`escapeExpression` 直出，超 100 字符或含换行才转 `<pre>` 弹窗），故可安全承载用户名字面 |
| `target_user_id` | 两条需要：`collection_owner_change` = 新 owner 的用户 id；`collection_invite_revoke` = **发起该次邀请的人**（`inviter_user_id`）的 id——admin 页会自动把它显示为用户，即「谁发的这条邀请」（受邀人则出现在 `details` 里）。core `StaffActionLogger#log_custom` 的 base_attrs **不含** `target_user_id` → 这两条须**直写** `UserHistory.create!`（`action: custom_staff` + `custom_type`）携带，照 core `log_access_control_list_permission_change` 先例；其余三条经 `StaffActionLogger.new(actor).log_custom` 常规路径即可 |

## 3. 注册 / 文案 / 可见性

- **下拉细分开关** = 符号在不在 `UserHistory.staff_actions`：plugin.rb `after_initialize` 里 `UserHistory.staff_actions.concat(%i[collection_name_change collection_intro_change collection_topic_note_change collection_owner_change collection_invite_revoke])`（去重追加）。不注册则无下拉条目，generic「plugin custom action」也匹配不到本日志（其按 `custom_type='custom_staff'` 字面匹配）。

- **筛选机制**：选中某 action → 前端同时传 `action_name` + `action_id`；服务端 `staff_action_records` 见 `action_id == 23` 即以 `action_name` 作 custom_type **精确过滤**（`WHERE action=23 AND custom_type='<name>'`）——非 action=23 一锅端。

- **可见性**：moderator 看不到 action=23（`can_see_staff_action_log?` 要求 action ∈ `moderator_visible_action_ids`，23 不在）→ **admin-only 审计模型**（与 chat 同构，属有意取舍）。

- **文案**：client locale（admin UI）加 `js.admin.logs.staff_actions.actions.<type>`（en / zh_CN）；缺 key 时行内显示 `[en:js.admin.logs.staff_actions.actions.X]` 方括号 key（i18n missing 回退），可读性差。

- `subject` **无「存 id 显名」钩子**（serializer / template 全透传、筛选用存储值全等）→ 不做分离映射，可读性靠 `subject` + `context` 布局达成。

## 4. 边界（现在不做）

- **独立表触发点**：当出现「需要 owner / 团队在专辑页读自己专辑的编辑史，或 moderator 自查前后值」等**非 admin 受众**时，`user_histories` 兜不住——那时才建独立表 + 插件查看 UI。勿提前建、勿为此自建 admin 查看页。
