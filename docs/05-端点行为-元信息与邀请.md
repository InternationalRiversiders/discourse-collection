# 端点行为：元信息与邀请

## 1. `PUT /collections/:id.json` — 改元信息（改名 / 改描述）

改元信息仍是建专辑（03 的 2）同一套字段与校验（body 与越界规则同之），区别只在谁可改、改谁的。

- 权限：该专辑 **owner**（改自己的）或 **staff**（改**任意**专辑，含他人专辑与无主专辑；admin 恒可，版主按设置，见 02 的 1）。owner 身份只能改自己创建的；管理操作正是为此给 staff 开的覆盖——**同名长度校验，staff 不豁免**（同 owner；清理不合规名 / 描述同样受 min / max 约束）。

- body：partial 更新（`name` / `description` 至少传一，可同传；与建专辑相同：`name` 去首尾空白后长度含边界 ∈ [min, max]、非空；`description` ≤ max）。越界 → 422。

- 行为：`updated_at=now`；`last_topic_added_at` **不动**（只有收录内容变动才动它）。`topic_count` 不动。

- **管理操作审计（见 10）**：**staff 以 staff 身份**改（即操作者**不是该专辑 owner**，含改他人专辑与无主专辑）才落审计——改名记 `collection_name_change`、改简介记 `collection_intro_change`。**改自己的专辑是常规编辑、不记**，staff 兼该辑 owner 时同样不记（未动用 staff 权限）；staff 兼共同维护者不在此列（共同维护者本无改元信息之权，仍属动用 staff 权限）。

- 响应：专辑对象完整形态。

## 2. 邀请（加维护者 / 换主，均需对方接受后生效）

> owner / 加维护者 / 换主一律**先发邀请、受邀人接受后**才落团队行 / 切换 owner（同意缓冲）。邀请记录在 `collection_invites`（`id SERIAL` / `collection_id` / `inviter_user_id` / `invitee_user_id` / `action_type` / `accept NULL|true|false` / `created_at` / `updated_at`）；owner / 加维护者 / 换主没有「不经同意即时生效」通道——**唯一例外 = staff 自邀接管**（2.7：发起者与受让人同为一人时同意无从谈起，校验通过即同事务内完成发起 + 接受；**对他人**仍无任何旁路）。

### 2.1 发起邀请 `POST /collections/:id/invites.json`

- body：`{ "user_id": int（已注册；≠ 发起者；或 == 发起者且命中 staff → 走 2.7 旁路）, "action_type": 0 | 1 }`。

- 权限与 `action_type` 校验：
  
  - `action_type=0`（邀成共同维护者）：**仅该辑现任 owner** 可发起；专辑无主 → 无人可发（该辑需先有主）。
  
  - `action_type=1`（邀成新 owner）：**现任 owner 或 staff** 可发起（owner 自主转让经邀请，见 02 的 1）；专辑**无主** → 仅 staff（staff 邀「指定首任 owner」）；owner **不能**指名自己（owner 自邀恒 422——非 staff 走 `invite_self_not_allowed`，staff 走 2.7 旁路的「已是 owner」拦截 `already_the_owner`）；**staff 指名自己 = 自邀接管**，不进本节常规流程、改走 2.7。

- 前置校验（发起时同步，单事务）：
  
  - 目标用户须已注册，否则 404；
  
  - 发起者 == 目标 → **非 staff** → 422（`invite_self_not_allowed`）；**命中 staff**（admin 恒可、moderator 按 `collection_moderators_can_manage_collections`）→ **本节后续步骤全部跳过，改由 2.7 承担**（同事务内完成发起 + 接受，响应 200 而非 201）；
  
  - `action_type=0` 目标身份前置：目标已在该辑有 `is_owner=false` 行（已是共同维护者）→ 422（`already_a_maintainer`，无需再邀）；目标为现任 owner 行 → 422（owner 变更走 `action_type=1`）。
  
  - `action_type=0` **目标准入（见 01 的 3）**：目标须命中 `collection_teamworker_allowed_groups` 且不命中 `collection_teamworker_disallowed_groups`（均为发起时现态），否则 422。
  
  - `action_type=0` **名额占位**：「现有 `is_owner=false` 行数 + 该辑有效未决（`accept IS NULL` 且未超 validity）`action_type=0` 邀请数」≥ `collection_max_teamworkers_per_collection`（默认 5，设 0 禁）→ 422；豁免角色 `collection_unlimited_teamworkers_role` 命中**发起者本人**则跳过（单选 `nobody|admin|staff`，默认 `nobody`）。名额在**发起时占位**、接受只落行（见 2.5），从源头限制可挂起的 pending 量；
  
  - 同辑已有**同 target 同 type** 的有效未决行 → **幂等返回既有行（200）**，不重复建；本短路排在**权限判定之后** —— 无本节权限者即便命中既有行亦 403，既有邀请的存在性不外泄（响应码不随「是否已有该行」变化）；
  
  - `action_type=1`：该辑已有**任一有效未决**换主邀请 → 422（每辑同时至多一条 `action_type=1` 未决，避免多 accept 竞争 owner 票面）；目标若已是共同维护者 → 允许（升主，见 2.5）；普通换主（有现任 owner 且目标非共同维护者）另有**共同维护者数门槛**：现共同维护者数已 ≥ `collection_max_teamworkers_per_collection` + 1 → 422（再换主接受后会把共同维护者推到 +2）；专辑**无主**（无旧主可 demote，数不变）、目标**已是共同维护者**（升主，数不变）与豁免角色 `collection_unlimited_teamworkers_role` 命中**发起者本人**不触发该门槛（详见 2.5 `action_type=1` 步 3）。**`设 0` 特例（cap=0）**：普通换主在此仍放行（现共同维护者 0 < 0+1），接受后旧主 demote 成为该辑**唯一 1 名**共同维护者——与 `action_type=0`「设 0 禁共同维护」（本条名额占位严格生效）不同，属**有意例外**（type=1 允许超上限 1 个，不随 type=0 设 0 而禁换主）；此后该辑再普通换主（现 1 ≥ 1）即被拦，旧主彻底除名经「移除维护者」端点完成即可（旧主本人自助离队，或新 owner 代为移除，02 的 3）。
  
  - `action_type=1` **目标准入（见 01 的 3）**：目标须命中 `collection_create_allowed_groups` 且不命中 `collection_create_disallowed_groups`（均为发起时现态），否则 422——成为新 owner 属「可拥有专辑」层级，与建专辑（03 的 2）同门槛；目标已是共同维护者（升主）同样须过此关，不能被「升级」成不被允许拥有专辑的人。

- 写入（单事务）：插一行 `collection_invites`（`accept=NULL`）。**不 bump** `collection.updated_at`（邀请是流程状态、非内容 / 元信息变更）；`topic_count` / `last_topic_added_at` 不动；不占团队行（仅计入占位）。

- 响应 **201** + 新建 invite 对象：`{ id, action_type, status: "pending", inviter, invitee, collection: {id, name}, created_at, expires_at }`（`expires_at` = `created_at` + validity；inviter / invitee 为用户对象）。

- **通知**：发邀请成功 → 入队通知受邀人（Discourse 原生通知系统，见 09 的 1）。

### 2.2 撤销邀请 `DELETE /collections/:id/invites/:invite_id.json`

- 权限：两条通路。
  
  1. **发起者本人**（默认通路）。
  
  2. **管理型 staff**：可撤销该专辑**任意有效未决的邀请**——**不限 `action_type`**（`action_type=0` 的加维护者邀请同样可撤）、**不限发起者**（owner 自主转让、staff 绕过 owner 发起的、乃至发起者已注销的行都在内）。判定 = 撤销者本人命中「管理操作」身份：admin 恒可；moderator 须开 `collection_moderators_can_manage_collections`（即 `CollectionPolicy#can_manage_collection?`，与本节 1 / 02 的 1 同口径）。既不命中、又非发起者本人 = **403**（`InvalidAccess`）。

- **动机**：邀请是管理动作留下的占位（尤其 staff 绕过 owner 发起的换主邀请会一直挡住新的换主发起），**管理团队应当能自己收尾**——否则除发起者本人无人能撤，发起者离职 / 失联、或只是一次误发时，只能干等 validity 过期。撤销权**不按邀请类型切分**：「该由谁来收尾」与 `action_type` 无关，多留一条类型判定只会让同一类残留行有的能清、有的不能清。

- **这不是越权**：管理组撤销的是**一条未决流程行**（= 叫停一次尚未生效的邀请），不触及团队行、不触及 owner、不改专辑内容。管理组对专辑**归属**仍没有任何强制旁路（要成为 owner 依旧只能走邀请并被对方接受；2.7 自邀接管仍是唯一「自己对自己」的例外），故本条不改变 02 的 1「管理 ≠ owner / teamworker」的口径。

- **审计（见 10）**：撤销**他人发起**的邀请 → 记一条 `collection_invite_revoke`；**撤销自己发起的不记**（本条按「是否代撤他人」判，与其余四型的判据都不同，见 10）。发起者已注销的行由管理组撤销时照记（该槽位落 `❌`）。写入字段与 `details` 的符号式拼法见 10 的 1。

- 行为：该行须为**有效未决**（`accept IS NULL` 且未超 validity），否则 422（`invite_not_pending`：已受理 / 已过期 / 已被撤）。**2.7 旁路行（`accept=true`）即属「已受理」**，不可撤（且发起者与受邀人同为一人，亦无撤的必要）。成功 = **物理删行**：占位**即时释放**、该行**不可再受理**、不出现在收件箱待决；被撤后可直接重邀（历史不挡重邀）。

- **边界**：判定只能用**撤销时刻的实时值**（`users.admin` / `moderator` 只有现态）——撤销者被降权后即失去此权，与其它管理操作同；行上不带任何「发起时」快照，故无历史口径可依。

- 响应 200。

### 2.3 专辑的邀请记录 `GET /collections/:id/invites.json`

- 权限：该辑 owner 或 staff（owner 看自己专辑的邀请管理；staff 管理操作可看任意专辑）。受邀人自己在收件箱看自己的条目，不在本端点拉取他人 pending。

- 行为：返回该专辑的邀请记录（待决 + 已受理历史 + 已过期，只要仍在 history 保留期内），按 `created_at desc`；通用分页。

- 响应每项：同 2.1 的 invite 对象（含 `status`：`pending|expired|accepted|rejected`，status 计算规则见 2.5）。**不返回 `can_revoke` 之类的判定字段**（撤销权改由前端自算）：2.2 的判定只取决于**查看者本人**是否管理型 staff，而 `currentUser.admin` / `currentUser.moderator` 与 `siteSettings.collection_moderators_can_manage_collections` 前端都有（与本节 1 / 02 的 1 同口径），行本身不携带任何服务端私有信息 → 撤销钮门控 = `status === "pending" && (inviter.id === currentUserId || 管理型 staff)`。

- **2.7 旁路行**以 `accepted` 出现，且 `inviter.id == invitee.id`（自邀接管留痕，前端可据此区分「staff 接管」与常规换主）；已受理故不在可撤销之列（2.2）。

### 2.4 受邀收件箱 `GET /collections/invites.json`

- 权限：**登录本人**（仅返回 `invitee_user_id = me` 的邀请；匿名 403，同 mine 口径——开 `collection_allow_anonymous` 亦不放开此「我的」端点）。同时是**本插件邀请界面**，与 Discourse 原生通知并存。

- 行为：返回我的邀请（只要仍在 history 保留期内），按 `created_at desc`；通用分页。`status` 计算（每项一个）：
  
  - `pending`：`accept` NULL 且 `created_at + validity > now`（可受理）；
  
  - `expired`：`accept` NULL 且 `created_at + validity ≤ now`（**仅展示、不可受理**）；
  
  - `accepted` / `rejected`：`accept` true / false（已受理历史，仍在 history 期内可查）。**2.7 旁路行**（`inviter == invitee == 本人`）也按此归入 `accepted` 历史——它从不处于 `pending`，故不影响本人收件箱的待决列表。

- 响应每项（给受邀人**足够决策信息**，不必再查专辑详情）：

  ```jsonc
  {
      "invites": [{
          "id": 37, "action_type": 1,
          "status": "pending",
          "inviter":   { "id": 100, "username": "xx", "name": "XX", "avatar_template": "/user_avatar/…/{size}.png" },
          "collection": { "id": 12, "name": "XX 阅读清单", "owner": { … } /* 可 null=无主，助受邀人判断 */ },
          "created_at": "2026-09-07T05:00:00.000Z",
          "expires_at": "2026-09-17T05:00:00.000Z"
      }],
      "meta": { "page": 0, "page_size": 30, "more": false }
  }
  ```

  不内嵌整专辑（受邀人可经详情端点再查）；`collection.owner` 快照助判断「有主 / 无主」（尤其 `action_type=1`「提为新 owner」时）。

### 2.5 受理（接受 / 拒绝）

- **公共前置**（accept / reject 相同）：该邀请存在且 `invitee_user_id = caller`，否则 404（不可见他人条目）；该行须**有效未决**（`accept` NULL 且未超 validity）——`expired` / `accepted` / `rejected` / 被撤 → 422（`invite_not_pending`）。

- **`POST /collections/invites/:invite_id/reject.json`（拒绝）**：不产生任何 membership / owner 写；`accept=false` 落库、占位释放。响应 200。

- **`POST /collections/invites/:invite_id/accept.json`（接受）**，单事务，逐 `action_type`：

  > **接受时准入复查（见 01 的 3）**：接受 ≠ 发起时快照——发起与受理之间受邀人可能已被移出允许组、或已被加入不允许组，故接受前置按 `action_type` 复查受邀人**当下**归属：`action_type=0` 须命中 `collection_teamworker_allowed_groups` 且不命中 `collection_teamworker_disallowed_groups`、`action_type=1` 须命中 `collection_create_allowed_groups` 且不命中 `collection_create_disallowed_groups`。不命中 → 422、**邀请保持未决（accept 仍 NULL）**、不触发换主 / 不加团队行、不发结果通知——与下述 `action_type=1` 步 0 的 collection cap 复查同「留待重试」语义（受邀人在 validity 内重新命中该组且不在不允许组后，可再接受）。拒绝不复查（拒绝只是 decline，不成为任何身份）。

  **`action_type=0`（成共同维护者）**：
  
  - 目标已在该辑有 `is_owner=false` 行（此前已被加 / 重复场景）→ 视为已是一致身份，**幂等成功 no-op**（仍将邀请置 accepted）；
  
  - 目标为现任 owner 行 → 422（owner 行的变动只能经 `action_type=1`，见下）；
  
  - 否则插一行 `(collection_id, invitee, is_owner=false)`。名额已在发起时占位，接受只落行（可留防御性复查）；
  
  - `collection.updated_at=now`；`topic_count` / `last_topic_added_at` 不动。

  **`action_type=1`（成新 owner）**：
  
  0. **接受前置 collection cap 检查**：新 owner 名下专辑数（其 `is_owner=true` 行，不含本辑）已 ≥ `collection_max_collections_per_user` **+1**（已超上限 1 个）→ 422（`ownership_accept_collection_limit_reached`），**邀请保持未决（accept 仍 NULL）**，不触发换主、不发结果通知；待降额后再接受即可。豁免角色 `collection_unlimited_collections_role` 命中**接受者本人**则跳过。换主路径对 collection cap **允许超上限 1 个**（存量 ≤ 上限可接受，成为 owner 后 ≤ 上限+1）；与创建（03 的 2，按上限 0 超出即拦）口径不同属设计。
  
  1. 受邀人置为该辑 owner 行：已有该辑团队行（共同维护者）则置 `is_owner=true` 升主；无则插 `(collection_id, invitee, is_owner=true)`；partial unique 同事务保证（至多一个 owner）。
  
  2. 专辑当前有现任 owner（非受邀人）：**恒 demote**——现任 owner 行 `is_owner true→false` 留任共同维护者；专辑**无主**（owner 删号等）则无事可做（接受即成为首任 owner）。
  
  3. 换主引起的共同维护者数变化受 `collection_max_teamworkers_per_collection` 约束（**允许超上限 1 个**）：普通换主（有现任 owner 且目标非共同维护者）接受后旧主 demote 使共同维护者 **+1** → 存量 ≤ 上限可发、接受后 ≤ 上限+1；发起时存量已 ≥ 上限+1 → 422（会到 +2）。**升已有共同维护者**（其行 false→true 与旧主 demote 抵消）与**无主专辑**（无旧主可 demote）不改变共同维护者数、不受此约束；豁免角色 `collection_unlimited_teamworkers_role` 命中**发起者本人**亦跳过（门槛在发起侧 2.1 执行，非接受侧）。
  
  4. 一致性（`subscribers_count`，见 02 的 5）：新 owner 受「成为 owner 即自动订阅」约束——其订阅行若已存在则保留、转为不计入的 owner 行，若未订阅则补一行；被 demote 的旧 owner 其订阅行仍在 → 因不再是 owner 而转**计入**（普通订阅）。事务后 `subscribers_count` **直接按规则重算**（= 该专辑订阅行数 − 当前 owner 行；owner 无订阅行则不减），不做逐人手工 ±。
  
  5. `collection.updated_at=now`；`topic_count` / `last_topic_added_at` 不动。
  
  6. **管理操作审计（见 10）**：本次换主若由 **staff 发起**（管理操作，含无主专辑指定首任），且在受邀人**接受落定**时 → 记 `collection_owner_change`；owner **自主转让**（owner 发起的 `action_type=1`）不记（属 owner 常规管理）。**2.7 自邀接管**同为 staff 发起的换主（且当场落定）→ 同样记一条（写入时机在发起请求的事务后，不必等接受）。
  
  - **恒 demote 只降身份、不锁人**：旧主留任共同维护者后即是普通共同维护者，可自行经该端点删本人 = 自助离队，彻底除名无须他人代劳；新 owner 若需代为移除，同一端点亦可（owner 移除任意共同维护者，02 的 3）。

- 响应（accept / reject 均 **200**）：接受返回更新后专辑对象**完整形态**（便于前端对账；`action_type=0` 只加维护、`action_type=1` 含 owner 变化）；拒绝返回 200（无专辑对象）。

- **通知**：接受 / 拒绝 → 入队通知发起者（接受时若发起者已不再是该辑 owner 仍通知，仅告知结果，见 09 的 1）。

### 2.6 两道时间闸 / 行生命周期（站点设置）

- `collection_invite_validity_days`（**server**，integer，**默认 10**）——受理窗口；`collection_invite_history_days`（**server**，integer，**默认 30**）——记录保留期。**均按 `created_at` 起算**；**交叉校验 validity ≤ history**（保存越界被拒）。**`history_days = 0` = 永久保留**（不清理、读端不过滤、validity 无上界）；其余（`history_days ≥ 1`）两校验器互相强制 `validity ≤ history`，二者均不允许负值。

- 生命周期（自 `created_at`）：`[0, validity]` 可受理 → `(validity, history]` 过期待决、`accept` 保持 NULL、不可再受理（2.5 前置 422）、行仍在（收件箱标 `expired`）→ `> history` 行被清理——**物理删**，由 scheduled job `PurgeCollectionInvites` 执行（每 `1.day` 跑一次、不钉钟点；受 `collection_enabled` 门禁），删 `CollectionInvite.out_of_history`（`created_at <= now − history_days`，即 `within_history` 之外）行——时间闸覆盖全态，`history_days ≥ 1` 时校验器保证 `validity ≤ history`，此类行必已过受理窗口、无未决可被误删。**`history_days = 0`（永久保留）**：`within_history` 恒全量、`out_of_history` 恒空，job 跑为 no-op，读端与磁盘都永久保留。接受 / 拒绝置 `accept` 后行保留至 history 到期（history = 0 则永久）。

- 重复邀请判定基础 = 存在「≤ validity 且 `accept` NULL」的行（已受理 / 已过期 / 被撤历史不挡重邀）。

### 2.7 staff 自邀接管（旁路）

> **动机**：staff 对他人专辑本只能改元信息 / 发起换主邀请；要**自己**接手一张专辑（代管、收拾无主专辑）时，「先发邀请、再自己接受」成了自问自答。故对「发起者 == 目标」开一条**旁路**：跳过同意缓冲（**同一事务内完成发起 + 接受**），但**两侧校验一条不减**，并落一行 `accept=true` 的邀请记录留痕。**旁路只对 `action_type=1` 成立**——能发 `action_type=0` 的只有该辑 owner，自邀即「目标为现任 owner」必被 2.1 前置校验拦下；对**他人**仍是邀请制、**无任何旁路**（旁路只作用于「自己对自己」，见 02 的 1）。

- **触发**：`POST /collections/:id/invites.json`，`action_type=1` 且 `user_id == 发起者本人`，且发起者命中「管理操作」身份——**admin 恒可；moderator 仅当 `collection_moderators_can_manage_collections` 开启**（同本节 1 / 02 的 1 口径）。非 staff 自邀仍走常规 422（`invite_self_not_allowed`）。

- **前置校验**（缺一即 422，**不落任何行、不改专辑**）：
  
  1. 发起者**当前不是**该辑 owner（无 `is_owner=true` 行）——已是 owner 则无换主可言 → 422（`already_the_owner`）。这条正是「admin 已经是 owner」的拦截点。
  
  2. 该辑**无有效未决** `action_type=1` 邀请（避免与别人正在进行的换主竞争）→ 422（`ownership_invite_already_pending`）。
  
  3. **准入复查（接受侧口径，见 01 的 3）**：发起者须命中 `collection_create_allowed_groups` 且不命中 `collection_create_disallowed_groups` → 422（`new_owner_not_in_create_allowed_groups`）。
  
  4. **collection cap（接受侧口径）**：发起者名下 `is_owner=true` 行数（不含本辑）已 ≥ `collection_max_collections_per_user` **+1** → 422（`ownership_accept_collection_limit_reached`）；豁免角色 `collection_unlimited_collections_role` 命中**发起者本人**则跳过。
  
  5. **teamworker cap（发起侧口径，允许 +1）**：该辑**有现任 owner**（普通换主，接受后旧主 demote 使共同维护者 +1）且现共同维护者数已 ≥ `collection_max_teamworkers_per_collection` **+1** → 422（`ownership_transfer_teamworker_limit_reached`）；专辑**无主**（无旧主可 demote，数不变）与**发起者本已是该辑共同维护者**（升主，数不变）不触发；豁免 `collection_unlimited_teamworkers_role` 命中**发起者本人**则跳过。

- **生效**（与 2.5 `action_type=1` 接受**完全同构**，同一事务，无等待期）：
  
  - 发起者置为该辑 owner（已有团队行 → `is_owner=true` 升主；无 → 插 `(collection_id, 发起者, is_owner=true)`）；partial unique 保证至多一个 owner；
  
  - 现任 owner（若有）**恒 demote** 留任共同维护者（2.5 步 2）；该辑**无主**则无事可做（发起者即首任 owner）；
  
  - 一致性照 2.5 步 4：发起者成为 owner 即**自动订阅**（订阅行转「不计入」的 owner 行，或补一行），被 demote 的旧主订阅行转**计入**，`subscribers_count` 事务后按规则重算；
  
  - `collection.updated_at = now`；`topic_count` / `last_topic_added_at` 不动。

- **留痕**：落一行 `collection_invites`——`inviter_user_id = invitee_user_id = 发起者`、`action_type=1`、**`accept=true`**（不是 NULL / 未决）。该行**不经受理、不可撤销**（2.2 只撤未决行）、**不占任何占位**、不发通知；失效日即 `created_at`、受 history 保留期约束（2.6）。它会在 2.3 邀请记录里以 `accepted` 行出现（`inviter == invitee` 即自邀接管），在**发起者本人的**收件箱（2.4）里同样只作为 `accepted` 历史出现（不影响其 pending 列表）。

- **审计（见 10）**：操作者是 staff 且动作是「改 owner」→ **记 `collection_owner_change`**（`subject` = 该辑；`target_user_id` = 新主即操作者；`previous_value` = 旧主用户名，无主专辑为空）；写入时机照「管理操作成功事务后」——本端点即该次请求的事务后，**不等任何人接受**。

- **通知**：**一律不发**——21076 收件人是受邀人、21077 收件人是发起者，此处二者同为一人，发给自己没有意义（见 09 的 1）。

- **响应 200**（与常规发起的 **201** 区分），一次性给出结果，免得前端再拉详情：

  ```jsonc
  {
    "invite": { "id": 41, "action_type": 1, "status": "accepted",
                "inviter": { /* … */ }, "invitee": { /* … 同一用户 */ },
                "collection": { "id": 12, "name": "…" }, "created_at": "…", "expires_at": "…" },
    "collection": { /* …专辑完整形态（owner 已换）… */ }
  }
  ```

- **前端契约**：①**换主弹层的用户选择器不得用 `excludeCurrentUser`**——旁路要能选到自己；排除名单只留「现任 owner」，而查看者本身就是 owner 时该 owner 即自己，故「owner 自邀」仍不可选（与后端 `already_the_owner` 一致）。「邀共同维护者」弹层的排除名单（现任 owner + 现有共同维护者）本就覆盖自己，不受影响。②响应判据 = **`invite.status`**：`pending` → 维持「已发送、等对方接受」态；`accepted` → **不进该态**，就地提示「你已成为该专辑的所有者」，并以响应里的 `collection` **重读页面**（owner / 团队卡 / 角色章 / 各入口门控全部变化，见 02 的 1 与 06 的 2）——结果随响应送达，不必再发一次详情请求。③发起入口门控不变：换主入口仍 = 现任 owner（自主转让）或 staff（任意专辑，含无主指定首任）。
