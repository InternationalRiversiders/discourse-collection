# 通知

## 1. 通知类型（自定义 `notification_type`）

本插件通知走 Discourse 原生通知系统。核心未给第三方预留数值段，故类型由插件在启动期向可变的 `Notification.types` 追加注册（`Notification.types[:collection_<x>] = <int>`），核心随即把该表原样下发前端（前端逆映射出符号名）。四型如下；后续加型按「收件人 + 该做什么 + 结果对团队有无真实变化」分型（受邀人内部只差文案，不拆型）：

| 数值 | 符号 | 收件人 / 入队点 / 去向 |
| -- | -- | -- |
| 21075 | `collection_topic_added` | 该专辑的订阅者（排除口径见 2）；收录成功后**登记待发批次**、静默期满入队；去向**专辑详情页** |
| 21076 | `collection_invitation` | 受邀人；发邀请成功时入队；去向插件收件箱（05 的 2.4）受理，`data.action_type` 0/1 分「邀共同维护者 / 邀成新 owner」文案 |
| 21077 | `collection_invitation_accepted` | 发起者；受邀人接受时入队；去向专辑详情页 |
| 21078 | `collection_invitation_declined` | 发起者；受邀人拒绝时入队（纯告知、无团队行 / owner 写）；去向专辑详情页 |

- 21077 在 type=1 接受、发起者已 demote 留任共同维护者的情形下**照常发送**——它只告知结果，不代表发起者仍有 owner 身份。

- **staff 自邀接管（05 的 2.7）不发任何通知**：两个收件人槽位（发起者 / 受邀人）同为一人，发给自己没有意义；该次换主只落邀请行与审计。

## 2. 订阅通知（21075）

收录（04 的 3）成功后**不立即建通知**，而是登记一个「待发批次」并起算 **1 分钟静默窗**。

- **合并（滚动防抖）**：窗口内每次新的收录都把窗口**重置**为 1 分钟，并并入同批。连续收录因此不断顺延，直到停手满 1 分钟才发；发出的是**一条**通知，覆盖整批，不逐话题拆条。设计意图：收录后往往还要接着收，等收完再一次性告知，避免连环打扰。

- **批次印记 = 该次收录插入的 membership 行 `created_at`**；job 醒来时现查该专辑**最新** membership 的 `created_at`，两者不等即**放弃发送**。三种情形由此一并判定：
  
  - 窗口内又收录了新的 → 最新行已换，本次 job 放弃，由后一次收录的 job 承担（合并语义）；
  
  - **由本次收录开启的那次收录被取消**（04 的 5）→ 最新行退回更旧的一行，**本次 job 放弃**，这一批不发。设计意图：收录后紧接着取消多为误操作，不该打扰订阅者；
  
  - **取消的是别的、更旧的话题** → 最新行未变，**本次 job 照发**。取消一个早就收了的话题，不构成「本批作废」的理由。

- **两个有意接受的边界**：①撤销只能拦住**尚未醒来**的 job——若某次收录的通知已因后继收录而放弃，此后再取消那次后继收录，也不会把它救回；②同一批里只有第一个通过判定的 job 会发（见下「实现约束」）。

- **不参与本机制**：幂等重收录（04 的 3 对已收录话题再 POST 一次）既不重置窗口也不起新批；精选变更（04 的 4）始终不通知。

- **收件人**（窗口期满时**现算**，非登记时快照）= 该专辑 `collection_subscribers` 全体 − **最后一次触发动作的操作者** − **已把最后一次收录话题的 OP 加入黑名单（忽略）**的订阅者（仅**未过期**的 active ignore，与核心话题列表折叠同口径，见 `app/models/topic.rb`；OP 为 staff 不排除）。订阅者把该话题设为免打扰等其它情形**不排除**。**owner 默认在列**（建专辑 / 成为 owner 即自动订阅，主动退订后不在）；排除只对操作者本人生效——共同维护者收录时不给该操作者发，此时未退订的 owner 仍收到。以「最后一次触发」为口径是**有意简化**：不为前序批次维护精确收件人集合。

- **呈现（两行槽位）**：第一行 = **专辑名**（走核心通知的 `display_username` 槽位），第二行 = i18n 文案「你订阅的淘专辑有更新」。**不带话题标题、不带操作者**——一批可能覆盖多个话题；`data` 为全体收件人共用且文案须可翻译，故只放定位键，句子由前端渲染器给出。

- **去向**：点击**一律进专辑详情页**（`/collections/:id`），不指向话题（一批可能覆盖多个话题）。`data` 只带 `collection_id` 供渲染器拼 href；本型不带 `topic_id` / `post_number`，核心的兜底链接为空——**链接必须由前端渲染器提供**。

- **实现约束**：不新增 DB 表 / 列、不加触发器。批次**没有待发标记**：延迟 job 由 `Jobs.enqueue_in(1.minute, …)` 投递，自身携带印记与「操作者 / 话题 OP」定位键即够；唯一的状态是 `PluginStore` 里每专辑一行「已发出的那个印记」，只用于**防重试重发**（job 发送前先认领该印记，发送途中崩溃被重排队时不会给全体再发一遍）。判定所依据的最新 membership 时间戳**现查现比**，因此没有任何标记需要清理：被取代或被取消的旧 job 一律靠「印记不再是最新」自行退出。

## 3. 邀请通知

21076 / 21077 / 21078 **不受静默窗影响——恒即时发送**，无合并 / 作废语义：发邀请成功 → 通知受邀人；接受 / 拒绝 → 通知发起者。三者同样走 Discourse 原生通知系统；`/collections/invites` 收件箱端点（05 的 2.4）保留作本插件独立的查看 / 受理界面，与原生通知并存。

## 4. 明确不做

- **owner 自主退出（彻底离队）**：owner **不能**把自己从专辑直接删除（无此端点）——彻底离队分两步：先经 type=1 邀请转让（接受后旧主恒 demote、留任共同维护者，见 05 的 2.5），再以共同维护者身份在「移除维护者」端点上删除本人 = 自助离队（02 的 3）。

- **无主专辑**：owner 删号后专辑成「无主」；改名 / 改描述由 staff（05 的 1）接手，指定首任 owner 由 **staff 发 type=1 邀请**（05 的 2.1，受邀人接受后生效）。删专辑端点只认 **owner 身份**、对 staff 身份不开口（06 的 2），但这不是死路：**管理型 staff** 可先经**自邀接管**（05 的 2.7，对无主专辑同样成立）把自己变成该辑 owner，再以 owner 身份调用删除端点——无主专辑仍有清理通道，只是要多一步。

- **限流**：反复订阅退订等纯**频率类**滥用仍不设计。恶意建专辑、以邀请骚扰特定用户等——见 01 的 3 的**不允许组**：把滥用者所在、或为其专设的群组加入 `collection_create_disallowed_groups` / `collection_teamworker_disallowed_groups`，其**创建专辑 / 成为新 owner / 被邀为共同维护者**即被拒；目标准入在**发起时**校验，**被反复邀请者可借此脱离骚扰**。判定按组、只在操作时刻发生，故**不回收**其在库的专辑与团队身份（01 的 3）。
