# 通知

## 1. 通知类型（自定义 `notification_type`）

本插件通知走 Discourse 原生通知系统。核心未给第三方预留数值段，故类型由插件在启动期向可变的 `Notification.types` 追加注册（`Notification.types[:collection_<x>] = <int>`），核心随即把该表原样下发前端（前端逆映射出符号名）。四型如下；后续加型按「收件人 + 该做什么 + 结果对团队有无真实变化」分型（受邀人内部只差文案，不拆型），**新增型从 21079 起顺延**：

| 数值 | 符号 | 收件人 / 入队点 / 去向 |
| -- | -- | -- |
| 21075 | `collection_topic_added` | 该专辑的订阅者（排除口径见 2）；收录成功后**入队（无延迟）**，既存通知**原地更新**而非逐次追加；去向**专辑详情页** |
| 21076 | `collection_invitation` | 受邀人；发邀请成功时入队；去向插件收件箱（05 的 2.4）受理，`data.action_type` 0/1 分「邀共同维护者 / 邀成新 owner」文案；`data.invite_id` 供邀请失效时定位该条通知（见 4） |
| 21077 | `collection_invitation_accepted` | 发起者；受邀人接受时入队；去向专辑详情页 |
| 21078 | `collection_invitation_declined` | 发起者；受邀人拒绝时入队（纯告知、无团队行 / owner 写）；去向专辑详情页 |

- 21077 在 type=1 接受、发起者已 demote 留任共同维护者的情形下**照常发送**——它只告知结果，不代表发起者仍有 owner 身份。

- **staff 自邀接管（05 的 2.7）不发任何通知**：两个收件人槽位（发起者 / 受邀人）同为一人，发给自己没有意义；该次换主只落邀请行与审计。

- **`data` 逐型**：21075 = `display_username`（专辑名）+ `collection_id`；21076 = `display_username`（发起者）+ `action_type` + `collection_id` + `collection_name` + `invite_id`；21077 / 21078 = `display_username`（受邀人）+ `action_type` + `collection_id` + `collection_name`。四型都**不含** `topic_id` / `post_number`，核心那些按话题定位的链接与清理因此一律够不着（见 4、5）。

- **呈现（两行槽位）**：第一行 = `display_username` 槽位（21075 为**专辑名**，21077 / 21078 为**受邀人用户名**，21076 为**发起者用户名**），第二行 = 前端渲染器给出的 i18n 文案。**链接一律由前端渲染器拼**（`collection_id` 走 `getURL`）——四型的 `data` 都不带核心认得的定位键，核心兜底链接为空。

## 2. 订阅通知（21075）

收录（04 的 3）成功后**入队一个 job（无延迟）**，每次收录各跑一次；job 就地**刷新**每位订阅者在该专辑上的那一条通知，而非逐次追加一条。

- **总闸 = 站点设置 `collection_topic_added_notification_enabled`**（默认开启）：关闭后收录**不排任何 job**，订阅者收不到收录通知；其余三型邀请通知（3）不受此设置影响。闸门只在**入队那一刻**：设置关闭前已排入的 job 照发，**不在 job 内复查**。

- **不做合并批**：收件人随本次收录的话题而变（话题不同，「拉黑 OP」与「可见性」两项判定的结果都不同），合并须另存「自上次发送以来收录了哪些话题」，其失准形态是漏发。故每次收录各跑一个 job。

- **不参与本机制**：幂等重收录（04 的 3 对已收录话题再 POST 一次）不排 job；精选变更（04 的 4）始终不通知；**取消收录（04 的 5）不发通知、也不撤回已发出的通知**——通知不带话题信息（见下「呈现」），无法自我更正。

- **收件人**（**发送时刻现算**，非收录时快照）= 该专辑 `collection_subscribers` 全体 − **本次收录的操作者**（不告知其自己的收录）− **已把本次收录话题的 OP 加入黑名单（忽略）**的订阅者（仅**未过期**的 active ignore，与核心话题列表折叠同口径，见 `app/models/topic.rb`；OP 为 staff 不排除）。订阅者把该话题设为免打扰等其它情形**不排除**。**owner 默认在列**（建专辑 / 成为 owner 即自动订阅，主动退订后不在）；排除只对操作者本人生效——共同维护者收录时不给该操作者发，此时未退订的 owner 仍收到。

- **可见性**（与收件人同一时刻现算）：口径 = **阅读页的列表口径**（`docs/04 §1`），三条：

  - **软删话题一律不发**（含 staff / mod 收件人）：阅读页的 feed 在 SQL 里写死 `topics.deleted_at IS NULL`，谁都不列；故这条**不交给收件人的 `can_see_topic?`** —— 它默认 `hide_deleted` 只挡普通人，对「能看该分类已删话题」的 moderator 会放行。
  - **unlisted 按收件人判**：仅对 `guardian.can_see_unlisted_topics?` 为真者（staff / TL4）发 —— 与阅读页 `scope.visible unless can_see_unlisted_topics?` 同一判据。unlisted 是**列表现则、不是可读规则**：普通订阅者点开话题 URL 读得到，但专辑页不给他列这一行，通知也就不该给他。
  - **其余**：话题的分类存在、分类非 `read_restricted`、**话题已 listed（`visible`）**、未软删、非 `shared_draft`、非 PM → 全部订阅者，不做逐人判定。快路径**要求 listed** —— unlisted 因人而异，必须落到下一路；其余情形（**含分类为 nil** —— 分类已删时 `can_see_category?(nil)` 为假，与「无限制分类」的结论相反）才逐收件人 `Guardian.new(user).can_see_topic?(topic)`。

  **勿自写组权限 SQL 替代**——任一条分支抄漏即泄漏或误伤。被过滤掉的人，其既存通知**既不顶置、`read` 也不重置**。

- **原地更新优先、缺失才新建**：本型通知不带 `topic_id`，其身份即 `(user_id, data->>'collection_id')` 这一对。job 一次查出本批人的既存行（**刻意不带 `read` 条件**——已读的老行正是要刷新的那条，带上就查不到、会另建，退回逐条累积）：**有既存行**者，同对多条只留 `id` 最大者、其余删除，保留行以一条 UPDATE 重写 `data`（专辑名可能已改）、置 `read=false`、并把 `created_at` / `updated_at` 顶到 now；**无既存行**者经 `Notification::Action::BulkCreate` 新建。`created_at` **必须显式写**：通知列表（全量页与用户菜单）只按它排，原地更新不动它就不会前移。

- **不变量 = 「至少一条」，非「至多一条」**：不引影子表（查不到即建 = 结构性自愈）、不加咨询锁（并发只可能「多」不可能「少」）、无兜底 job（重复最多活到该专辑的下一次收录被坍缩；此后不再收录则长期留存）。**job 幂等**：重投递时上次写的行已存在 → 全走更新路径收敛。

- **推送**：`update_all` / `delete_all` 绕过 AR 回调，而核心的实时推送正挂在回调上 ⇒ 刷新路径必须**显式对受影响者 `publish_notifications_state`**（新建路径由 `BulkCreate` 自带，**不要重复推**）。漏推症状 = 新收件人实时出现、被更新的老收件人不动。

- **呈现**：第一行 = **专辑名**（核心的 `display_username` 槽位），第二行 = i18n 文案「你订阅的淘专辑有更新」。**不带话题标题、不带操作者**——一条通知说的是「该专辑有更新」，不指名话题；`data` 为全体收件人共用且文案须可翻译，故只放定位键，句子由前端渲染器给出。去向**一律**专辑详情页（`/collections/:id`）。

- **有意取舍**：①高频收录会反复顶置 + 反复置未读，**不做节流**；②权限事后放开不补发、收回不回收（判定时刻 = 发送时刻）。

## 3. 邀请通知

21076 / 21077 / 21078 **恒即时发送**（消息一产生即入队），每次各新建一行，不参与 2 的原地更新与坍缩。三型同样走 Discourse 原生通知系统；`/collections/invites` 收件箱端点（05 的 2.4）保留作本插件独立的查看 / 受理界面，与原生通知并存。

## 4. 通知的清理

**核心够不着这一侧（结构性）**：核心处理「被删对象」的通知分三层——写时定点删（`PostDestroyer#remove_associated_notifications`）、权限收回时定点删（`Topic#remove_allowed_user` 与 `DeleteInaccessibleNotifications`）、读时过滤与定期兜底（`Notification.visible` 按 `topics.deleted_at IS NULL` 隐藏、`Notification.ensure_consistency!`）——**三层都锚在 `topic_id`（+ `post_number`）上**，而本插件四型都不带这两个键：`visible` 的 `LEFT JOIN` 对 `topic_id IS NULL` 恒判保留，`ensure_consistency!` 不覆盖非 `high_priority` 行。故**专辑删除后这些通知不会自行消失**，且残留**计入未读红点**（`unread_notifications` / `all_unread_notifications_count` 都走 `LEFT JOIN topics … t.deleted_at IS NULL`，对 NULL 判真），必须本插件自删。

**勿为「让核心帮我清」而给通知填 `topic_id`**：填上会让核心那三层按「通知所讲的那个话题」隐藏 / 删除它们，与「专辑」语义不符——该话题一旦被删，通知就会莫名消失。缺 `topic_id` 是有意的。

**专辑删除：四型全删。** 四型去向在专辑删除后都已不可达：

| 型 | 收件人 | 去向 | 专辑删除后 |
| -- | -- | -- | -- |
| 21075 订阅 | 订阅者 | `/collections/:id` | 404 |
| 21076 邀请 | 受邀人 | `/collections/invites` | 邀请行由外键 CASCADE 删除，点进去收件箱里无对应项 |
| 21077 已接受 | 发起者 | `/collections/:id` | 404 |
| 21078 已拒绝 | 发起者 | `/collections/:id` | 404 |

落点 = `Collection::Delete` **删除事务提交后**入队的 `Jobs::DiscourseCollection::PurgeCollectionNotifications`（**异步**，代码在 `app/jobs/regular/discourse_collection/`）。条件 = 四型 + `data->>'collection_id'` 等于该专辑 id。该 job **先取受影响者、再 `delete_all`**（`delete_all` 绕过 AR 回调，而实时推送挂在回调上），随后逐个补推 `publish_notifications_state`（须用**新载入的 `User`**，计数按实例 memoize）。`->>` 取出来是**文本**，比较值写 `collection_id.to_s`。条件里**仍写 `notification_type`**，作为「只认本插件四型」的保险。**不分型删**：`notifications` 上没有以 `notification_type` 打头的索引，删一型与删四型的执行计划与成本相同，而部分删只会把口径劈成「状态型删、历史告知型留」，后者照样 404。job **按定位键删，故幂等**（重投递删剩下的）；**不设 `collection_enabled` 门禁**（门禁关掉后已入队的清理仍须跑完，与 `PurgeCollectionInvites` 等 job 的门禁写法不同）。

**为何异步**：该查询是 `data::jsonb ->> 'collection_id' = ?`——`notifications.data` 是 `varchar(1000)`，该条件是查询期转型的表达式。两个条件**都只能当过滤、没有可用的访问路径**：`notification_type` 没有以它打头的索引（全表仅两条索引含 `notification_type`——`idx_notifications_speedup_unread_count` / `index_notifications_user_menu_ordering_deprioritized_likes`——均以 `user_id` 打头，本查询无 `user_id` 条件），`data` 上的表达式索引只有 core 为固定键建的那几条。计划因此是**全表顺序扫描**，且同一谓词跑两遍（`distinct.pluck` 一遍、`delete_all` 一遍）——**扫描代价正比于全站通知总量**而非专辑自身大小，留在请求内会让删除端点的响应时间随论坛通知量增长。表达式求值不随全表走：同一节点的两个条件由规划器按每行估算成本重排（`order_qual_clauses`，估计结果、非契约保证），整数比较在前、AND 短路，`jsonb` 转型只落在该型命中的行上。**不为它建索引**：`notifications` 上那几条 `data` 表达式索引（`index_notifications_on_data_display_username` 等）是 core 为**核心自身及其捆绑插件**建的，第三方插件在核心表上建索引**没有 core 的版本与存续保证**（core 改列 / 改类型 / 清索引都不对本插件承诺），故不采。入队落在**事务提交后**的 step：事务内入队会让回滚掉的删除把一个仍存在的专辑交给 job。

**该异步化的代价**：提交到 job 跑完之间存在窗口，其间这些通知仍指向已删专辑（21075 / 21077 / 21078 点开 404；21076 指向的收件箱已无对应项）。删除回滚不产生残留（入队在提交后），但**提交后入队前进程中断、或 job 丢失**，则这批通知不再有任何机制会碰到——残留计入未读红点（见本节开头），核心与本插件两侧都无清理路径。

**邀请失效：删该邀请的 21076。** 21076 是「等你答的一道题」，题没了（被撤销、被本人受理）通知就不该留在列表里——它指向 `/collections/invites`，而收件箱里那一条要么已经不在，要么状态与通知的口气不符。**去重键必须落到邀请行上**：同一人可**同时**持有同一专辑的 `action_type=0` 与 `=1` 两条 pending 邀请（控制器的幂等短路键带 `action_type`，且无步骤禁止两型并存），按 `(user_id, collection_id)` 删会误伤另一条仍在等答的邀请；`action_type` 也不能代替（同型的两条新老邀请会撞在同一个 `(user, collection, action_type)` 键上）。故 21076 的 `data` 带 `invite_id`（21075 / 21077 / 21078 不带），清理一律按它定位，查询另加 `user_id = 受邀人` 收窄。

| 时机 | 落点 | 删除条件 |
| -- | -- | -- |
| 邀请被撤销（发起者撤回，或 staff 代理撤回） | `Collection::RevokeInvite` 事务内，与 `destroy_invite` 同事务 | 该 `invite_id` 的 21076，且 `user_id` = 受邀人 |
| 受邀人本人接受 / 拒绝 | `Collection::AcceptInvite` / `Collection::RejectInvite` 事务内 | 同上 |

- 删除走 `delete_all`，绕过 AR 回调（见 2 的「推送」）⇒ 事务提交后对受影响者补推 `publish_notifications_state`；补推的收件人由事务内的 step 写进 context（撤销路径的记录届时已 `destroy!`，不可在事务后读邀请）。
- 受邀人从未收到过 21076（job 未跑、或行已被核心清理）时，删除是空操作。
- **只动 21076**：21077 / 21078 是发给发起者的结果告知，其对象（专辑）仍在，不受影响。
- 收件箱页本身不置读（与核心「打开列表不置读」一致）；21076 的已读由「被本人受理」这一步的删除一并解决，故不需单独的已读路径（5）。

**不清理的情形**：邀请过期（越 `collection_invite_validity_days`，行保留、状态 `expired`）、邀请行被 `PurgeCollectionInvites` 物理清除（越 `collection_invite_history_days`）、受邀人被移出准入组——三者都由时间或组变更推动，没有「发生的一刻」可挂清理，其 21076 残留不处理。

## 5. 通知的已读

**核心够不着这一侧（结构性）**：核心把通知置已读只有两条路——**点那一条通知**（前端写 `Discourse-Clear-Notifications` header 与 `cn` cookie，后端在下次请求收割，走 `Notification.read(user, ids)`，纯按 id）与**显式 dismiss**（`notifications_controller#mark_read`，按 id / 按 type / 全清）。而「到达通知所讲的对象即已读」在核心只有一处：`Notification.mark_posts_read(user, topic_id, post_numbers)`，由 `POST /topics/timings` 在浏览话题时调用，**要求 `topic_id` 与 `post_number` 双匹配**。四型都不带这两个键 ⇒ 该链永不命中 ⇒ **进专辑详情页、进收件箱都不会已读**，只有点通知才清。

**决定**：进入专辑详情页，即置读该访问者在该专辑上的未读通知（**21075 / 21077 / 21078 三型**，去向同为专辑详情页）。这一侧的动作是**置读**而非删除：对象还在，只是「已看过」。**21076 不在此列**——它指向收件箱，且「被本人受理」那一步已经把它删掉（4）；单纯打开收件箱不置读，与核心「打开列表不置读」一致。

- **端点**：`PUT /collections/:id/read_notifications.json`（02 的 6）。action 挂 `BaseController#ensure_write_access`——置读是写操作，游客在进 service 之前即被拦下（游客的 `guardian.user` 是 `nil` 而非「带空 user_id 的对象」，不挂这道门会直接 500 而非 403）；专辑不存在由 `find_collection` 404。

- **入参只有 `:id`（专辑 id）**，不接受通知 id 名单：客户端没有可靠的 id 来源——核心下发给前端的只有按类型的**计数**（`grouped_unread_notifications`），唯一的 id 来源是 `recent-notifications` 那个 Ember store 缓存，要先在用户菜单或通知页加载过才有内容。一次请求按 `collection_id` 覆盖该专辑上的**全部**未读行。**不设订阅门**：只动调用者自己的行，与其是否订阅无关。

- **服务端**：按 `user_id + 三型 + read: false + data->>'collection_id'` 取出未读 id → `Notification.read(user, ids)`（核心的置读 API，自带 `user_id` 收窄与幂等）——**勿手写 `update_all`**。查询只落在**一个用户**身上（走核心那条 partial `(user_id, notification_type) WHERE NOT read`；退一步也只扫该用户的行）；**无未读时不写库、不补推**。有变更则提交后对调用者补推 `publish_notifications_state`（`update_all` 绕过 AR 回调；计数按实例 memoize，故补推须用**新载入的 `User`**）。

- **前端门**：落 `routes/collections-show.js` 的 `setupController`（**非 model hook，故 404 时不发**）：判定 `shouldMarkCollectionNotificationsRead(currentUser, site)` 在 `lib/collection-notifications.js`（自带单测），报文函数 `markCollectionNotificationsRead(id)` 在 `lib/collection-api.js`，即发即忘、失败静默。门读 `currentUser.grouped_unread_notifications` 的三型计数（类型 id 取自 `site.notification_types.collection_*`），**三型全 0 或字段缺失即不发请求（fail-closed）**：失效形态 = 通知保持未读，与现状一致、可观测、可手动点击清除，且不会把「门坏了」伪装成正常。**门按型不按专辑**：浏览 B 专辑而未读落在 A 专辑时门照开，服务端查空即空操作——精度只到「型」是有意接受的取舍（计数不带 `data`，MessageBus 载荷只带最新一条），更细的本专辑级判断须另引边表，不做。

- **停留期间的新收录不置读**：详情页不会自动重取，用户看不见刚落进来的话题，此时置读是把「没看到」谎报成「看过」。真正的置读发生在用户点通知回到同一页时——那一次由核心完成：`DiscourseURL.routeTo` 在路径相同时显式调 `routerService.refresh()`，该 route 的 model 与 `setupController` 随之重跑，页面因此显示新收录的话题；同时核心在点击那一刻已**就地**置读该条并递减计数，刷新后门看到计数已归零，不会为同一条再发一次请求。

## 6. 不发邮件

四型**一律不发邮件**。默认不置 `skip_send_email` 时邮件链是这样走完的：21076 / 21077 / 21078 用 `Notification.create!`，其 `after_commit :send_email, on: :create` 会执行；21075 走 `Notification::Action::BulkCreate`，它用 `insert_all!` 并**自行补做**核心那三个 after_commit 回调（推送、邮件、`DiscourseEvent`）。两条路最终都落到 `NotificationEmailer.process_notification`，而它按类型名在 `EmailUser` 上找不到同名方法即返回 ⇒ **不产生任何邮件**。隐式成立的唯一残余代价：收件人在免打扰时先写一行 `shelved_notifications`，由 `Jobs::ProcessShelvedNotifications`（每 5 分钟一次）读出并删除（投递同样是 no-op）。

- **新建路径一律显式 `skip_send_email`**（两处 `Notification.create!` 置该键；21075 的 `BulkCreate` 传 `skip_send_email: true`）：不依赖「恰好没有对应邮件方法」这层隐式保护——核心日后给 `EmailUser` 补上同名方法、或另一插件注册邮件过滤器，都会让这层保护失效；同时也免掉免打扰用户的 `shelved_notifications` 写入。
- **更新路径走 `update_all`**（2），本就不触发回调。

## 7. 明确不做

- **owner 自主退出（彻底离队）**：owner **不能**把自己从专辑直接删除（无此端点）——彻底离队分两步：先经 type=1 邀请转让（接受后旧主恒 demote、留任共同维护者，见 05 的 2.5），再以共同维护者身份在「移除维护者」端点上删除本人 = 自助离队（02 的 3）。

- **无主专辑**：owner 删号后专辑成「无主」；改名 / 改描述由 staff（05 的 1）接手，指定首任 owner 由 **staff 发 type=1 邀请**（05 的 2.1，受邀人接受后生效）。删专辑端点只认 **owner 身份**、对 staff 身份不开口（06 的 2），但这不是死路：**管理型 staff** 可先经**自邀接管**（05 的 2.7，对无主专辑同样成立）把自己变成该辑 owner，再以 owner 身份调用删除端点——无主专辑仍有清理通道，只是要多一步。

- **限流**：反复订阅退订等纯**频率类**滥用仍不设计。恶意建专辑、以邀请骚扰特定用户等——见 01 的 3 的**不允许组**：把滥用者所在、或为其专设的群组加入 `collection_create_disallowed_groups` / `collection_teamworker_disallowed_groups`，其**创建专辑 / 成为新 owner / 被邀为共同维护者**即被拒；目标准入在**发起时**校验，**被反复邀请者可借此脱离骚扰**。判定按组、只在操作时刻发生，故**不回收**其在库的专辑与团队身份（01 的 3）。
