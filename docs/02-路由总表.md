# 路由总表

> `collections` 下的字面段（`mine`、`subscribed`、`invites`）路由声明必须放在 `:id` 之前（收件箱 `GET /collections/invites` 与 mine / subscribed 同理是本人跨专辑维度，非 `:id`）。

## 1. 专辑（元信息）

| Method | Path | 权限 | 行为 |
| -- | -- | -- | - |
| POST | `/collections.json` | 登录 + 命中创建准入组（见 01 的 3） | 创建专辑 |
| GET | `/collections.json` | 读 | 专辑列表（排序 / 翻页 / 按用户名过滤其创建或维护的专辑） |
| GET | `/collections/:id.json` | 读 | 专辑详情（元信息 + 维护者 + 订阅态 + 该 owner 的其他专辑，见 03 的 4） |
| PUT | `/collections/:id.json` | owner；staff | 改名 / 改描述（owner 改自己的；staff 可改任意专辑，见 05 的 1） |
| DELETE | `/collections/:id.json` | owner | 删专辑（级联清收录 / 精选）；**端点不认 staff 身份**，staff 须先经 05 的 2.7 自邀接管成为 owner |
| GET | `/collections/mine.json` | 本人 | 我创建 ∪ 我维护（去重）的专辑列表 |

> 下文「staff」「管理操作」指站点员工：**admin 恒可**；moderator 仅当站点设置 `collection_moderators_can_manage_collections` 开启（默认关）时可。**管理 ≠ owner / teamworker**——staff 对专辑的「管理操作」（改名 / 改描述（05 的 1）与**发起换主邀请 `action_type=1`**（05 的 2.1，含无主专辑指定首任））作用于**任意专辑**（含他人创建、无主），与操作者是否该专辑的 owner / 共同维护者无关；换主邀请的对象同样须接受后才生效——**唯一例外 = 选中自己**（05 的 2.7 staff 自邀接管：同一人谈不上同意缓冲，当场落定）。自己的专辑用 owner 身份即可（owner 自主转让的 type=1 邀请不经此开关，owner 恒可发起自己的专辑）。**管理操作自动记入管理操作审计日志**（见 10）。
>
> **owner / 加维护者 / 换主一律经「邀请制」**（见下「邀请」节）：成为共同维护者、成为新 owner 都先发邀请、对方**接受后**才生效（同意缓冲）。移除共同维护者不需要对方同意，仍保留 owner 直接 `DELETE`。

## 2. 收录（专辑阅读页）

| Method | Path | 权限 | 行为 |
| -- | -- | -- | - |
| GET | `/collections/:id/topics.json` | 读 | **专辑阅读页**：按收录时间列话题；`has_selected_reply=true` 的话题自带本专辑的精选回复 |
| POST | `/collections/:id/topics.json` | owner / teamworker | 收录主题 `{topic_id, note?}` |
| PATCH | `/collections/:id/topics/:topic_id.json` | owner / teamworker | 更新单条收录：改 note + 精选 / 取消精选（增量 body，见 04 的 4） |
| DELETE | `/collections/:id/topics/:topic_id.json` | owner / teamworker | 移除收录（连带清该收录的精选、重算冗余） |
| PUT | `/collections/:id/topics/:topic_id/note.json` | staff | 改写话题备注（仅 note；修正不合规内容，见 06 的 1） |
| GET | `/collections/:id/topics/:topic_id/selected_replies.json` | 读 | 某收录话题的精选回复全量（翻页；阅读页内联溢出时按需查，见 04 的 2） |
| GET | `/collections/:id/topics/:topic_id/selected_replies/count.json` | 读 | 某收录话题的精选回复**行数**（移除收录前的级联告警用，见 04 的 7） |

> **改写话题备注 ≠ 专辑「管理操作」**（见 06 的 1）：改 note 让 **admin 恒可、moderator 恒可**改写**任意**专辑（含他人专辑、无主专辑）里单条收录的 `note`，凡操作者判断该备注不合规 / 不当即可改——**不随** `collection_moderators_can_manage_collections` 开关（那条开关只管专辑级管理操作改名 / 改描述 / 发起换主邀请，见上方「专辑（元信息）」注），也不要求操作者是该专辑 owner / 共同维护者。是否「不合规」由操作者自行判断，系统无自动判定。
>
> 精选回复的**写**无独立端点：新增 / 取消精选并入 PATCH（04 的 4），body 以不同字段区分、按需发送。**读**：默认随上面 GET 阅读页内联返回；每话题内联条数受 `collection_max_selected_replies_per_topic`（默认 3）上限，溢出时经 `GET /collections/:id/topics/:topic_id/selected_replies.json` 翻页查全量（见 04 的 1、04 的 2）。

## 3. 共同维护者（owner 移除 / 本人自助离队）

| Method | Path | 权限 | 行为 |
| -- | -- | -- | - |
| DELETE | `/collections/:id/teamworkers/:user_id.json` | owner / 本人 | 移除维护者 / 本人离队 |

> **「添加维护者」已并入邀请制**（见下「邀请」节 / 05 的 2.1 `action_type=0`）：owner 不能直接加人——先发邀请、对方接受后才成为共同维护者。**移除**被移除者无需同意，故保留 owner 直接 `DELETE`；同一端点亦开放共同维护者**删除本人** = 自助离队（移除他人仍仅 owner，语义见下）。
>
> 维护者**读取无独立端点**：团队随专辑详情（03 的 4，完整形态）一起返回（`owner` 可 null + `teamworkers` 数组），共同维护者数组规模本就受上限约束（默认 ≤5），独立列表端点冗余。
>
> 「维护者」= `collection_teamworkers` 中 `is_owner=false` 的行（owner 单独建模，不计入维护者与上限）。
>
> **DELETE（owner 移除 / 本人离队、非幂等）**：调用方二——owner 移除任意共同维护者；共同维护者删除**本人** = 自助离队（移除队友仍仅 owner，越权 403）。目标当前不是该专辑共同维护者（无 `is_owner=false` 行）→ 422；目标为 owner 本人（`is_owner=true` 行）→ 422（owner 行的变动走换主邀请 `action_type=1`，不经移除；owner 亦不能经此删自己——彻底离队走 05 的 2 转让）；成功 = 删该行 + 同事务 bump `collection.updated_at`（见 08）；`topic_count` / `last_topic_added_at` 不动。换主中被 demote 的旧主留任共同维护者，因此彻底除名走的也是本端点——旧主本人自助离队即可，新 owner 亦可代为移除（见 05 的 2.5）。

## 4. 邀请（加维护者 / 换主，均需对方接受）

| Method | Path | 权限 | 行为 |
| -- | -- | -- | - |
| POST | `/collections/:id/invites.json` | owner / staff | 发起邀请 `{user_id, action_type}`；`action_type=0` 邀成共同维护者（仅 owner）、`=1` 邀成新 owner（owner 或 staff）；**staff 把 `user_id` 填成自己 = 自邀接管**（05 的 2.7，当场生效、响应 200） |
| GET | `/collections/:id/invites.json` | owner（该辑）/ staff | 该专辑的邀请记录（待决 / 已受理 / 已过期，供 owner 管理） |
| DELETE | `/collections/:id/invites/:invite_id.json` | 发起者本人；管理型 staff（该辑任意未决邀请） | 撤销未决（pending）的邀请（自己发起的，或管理组代撤他人发起的；代撤记审计，见 05 的 2.2） |
| GET | `/collections/invites.json` | 本人 | **受邀收件箱**：我收到的邀请（含待决 / 已受理历史；字面段，`mine` / `subscribed` 同法前置） |
| POST | `/collections/invites/:invite_id/accept.json` | 受邀人本人 | 接受邀请（逐 `action_type` 语义见 05 的 2.5） |
| POST | `/collections/invites/:invite_id/reject.json` | 受邀人本人 | 拒绝邀请（不产生任何 membership / owner 写） |

> 邀请记录在 `collection_invites`（**流程表**，代理主键 `id SERIAL`），带 `action_type`（0 = 邀共同维护者、1 = 邀成新 owner）与 `accept`（NULL 未决 / true 接受 / false 拒绝）。**两道时间闸**均由站点设置控制、按 `created_at` 起算：**受理窗口** `collection_invite_validity_days`（默认 10，期内可接受 / 拒绝，超期 `accept` 保持 NULL、不可再受理）与**记录保留期** `collection_invite_history_days`（默认 30，超期行被清理）；两设置交叉校验 validity ≤ history（history 可设 **0 = 永久保留**、不清理，此时 validity 无上界；详见 05 的 2.6）。收件箱同时是本插件的邀请界面，与 Discourse 原生通知（自定义 notification type）并存。详细语义（发起前置校验 / 占位、受理事务、owner 恒 demote、`subscribers_count` 重算）见 05 的 2。

## 5. 订阅

| Method | Path | 权限 | 行为 |
| -- | -- | -- | - |
| POST | `/collections/:id/subscription.json` | 登录 | 订阅（幂等；owner 建专辑即自动订阅，退订后仍可再订） |
| DELETE | `/collections/:id/subscription.json` | 登录 | 退订（幂等） |
| GET | `/collections/subscribed.json` | 本人 | 我的订阅列表 |
| GET | `/collections/:id/subscribers.json` | 读 | 订阅者列表（公开，可翻页） |

> 「订阅」以当前访问者为对象记录在 `collection_subscribers`（每专辑每用户至多一行）。**owner 例外**：建专辑 / 成为 owner 时即**自动订阅**（落一行 owner 订阅行），但 owner 是唯一「订阅但不计入 `subscribers_count`」的人；owner 可退订（此后共同维护者加内容时不再被通知），也可再订阅。任意登录用户订阅 / 退订均幂等（未订阅时 POST 即订阅、DELETE no-op 200）。专辑对象的 `is_subscribed` = 当前访问者在该专辑是否有订阅行（owner 未退订时为 true；匿名恒 false），见 03 的 1。计数与公开订阅者列表同口径 = 订阅行数 − 当前 owner 行（owner 不出现在订阅者列表），见 03 的 1。
>
> **响应**：订阅 / 退订成功均返回专辑对象**完整形态**（含更新后的 `is_subscribed` / `subscriber_count`；幂等 no-op 同）；`GET /collections/:id/subscribers.json` 返回 `{ "subscribers": [用户对象…], "meta": {…} }`——**计入口径**（owner 恒不在列）、按订阅先后 `created_at` **升序**、通用分页（meta 同其它列表）。
