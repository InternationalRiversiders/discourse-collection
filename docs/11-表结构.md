# 表结构

本插件共 6 张表。下方逐表给出建表语句、用途、查询业务与索引；**schema 的权威是 [`db/migrate/`](../db/migrate/)**，本文件是它的叙述版。

五条贯穿全部表的约定（均有意偏离 core 惯例）：

- **每张表都有真主键**：关联表用复合主键，实体表 `collections` 与流程表 `collection_invites` 用自增 `id SERIAL`。

- **外键一律内联**在列定义里（`REFERENCES … ON DELETE CASCADE / SET NULL`）。core 几乎不建外键，本插件有意偏离——级联清理交给 DB，不靠触发器。

- **每条外键的引用列都有索引**。这是上一条的代价：PG 的 `ON DELETE CASCADE` / `SET NULL` 按被引用行的键对子表做 `DELETE` / `UPDATE … WHERE 引用列 = 键`，缺索引时外键侧每删一行就要扫一遍子表。

- 冗余列由**业务层在同一事务里原子维护**，**无 DB 触发器**：`collections.topic_count` / `last_topic_added_at` / `subscribers_count`、`collection_topics.has_selected_reply`；`updated_at` 同理，由写入方置值（见 08）。

- 主键之外**只有下面逐表列出的索引**，无其它辅助索引。

## 1. `collections`

```sql
CREATE TABLE collections (
  id SERIAL PRIMARY KEY,
  name CHARACTER VARYING(100) NOT NULL,
  description CHARACTER VARYING(1000) NOT NULL,
  topic_count INTEGER NOT NULL DEFAULT 0,
  subscribers_count INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_topic_added_at TIMESTAMP
)
```

**表用途**：专辑的元信息，一行一张专辑。专辑名不唯一，故用自增代理主键。

**查询业务**：

- 专辑列表（03 的 3、04 的 6）：按 `created_at` / `last_topic_added_at` / `topic_count` / `subscribers_count` 排序，可限全站或指定用户，翻页。

- 专辑详情（03 的 4）：按 `id` 取一行。

- 另 5 张表都按 `id` JOIN 本表。

- `name` / `description` 的列宽与站点设置的上限一致（`VARCHAR(100)` / `VARCHAR(1000)`），长度校验只在业务层做（03 的 2）。

**冗余列**：`topic_count`、`last_topic_added_at`、`subscribers_count`。`last_topic_added_at` **可空**，`NULL` = 从未收录、排序时视为最旧（见 01 的 8）；`subscribers_count` = 该专辑订阅行数 − 当前 owner 行（03 的 1）。

**索引**：

```sql
CREATE INDEX index_collections_on_created_at
    ON collections USING btree (created_at)

CREATE INDEX index_collections_on_last_topic_added_at
    ON collections USING btree (last_topic_added_at DESC NULLS LAST)

CREATE INDEX index_collections_on_topic_count
    ON collections USING btree (topic_count)

CREATE INDEX index_collections_on_subscribers_count
    ON collections USING btree (subscribers_count)
```

四个可排序字段各一条，服务列表的排序与翻页（03 的 3）；`order` 的两个方向由同一条索引的正向 / 反向扫描共用，故四条覆盖全部八种组合。`last_topic_added_at` 可空，排序方向与空值位置由 controller 逐字指定（降序 `NULLS LAST`、升序 `NULLS FIRST`），索引必须声明成一致的方向与空值位置才匹配得上——btree 的默认形态（升序 `NULLS LAST`）两个方向都匹配不上。

## 2. `collection_topics`

```sql
CREATE TABLE collection_topics (
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  topic_id INTEGER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
  note CHARACTER VARYING(100),
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  has_selected_reply BOOLEAN NOT NULL DEFAULT false,
  PRIMARY KEY (collection_id, topic_id)
)
```

**表用途**：专辑与话题的对应关系，一行 = 某专辑收录某话题。`note` 是收录者写的备注（上限 100 字符，业务层常量，见 04 的 4）。

**查询业务**：

- **某话题被哪些专辑收录**（07 的 1）：话题页每次打开都要查，是本插件最热的查询（高频单行查）。

- **某专辑收录了哪些话题**，按 `created_at` 排序 + 翻页（04 的 1）。

- 移除收录、重算 `last_topic_added_at`（04 的 5、08 的 1）也落在这张表上。

**冗余列**：`has_selected_reply`——阅读页取出一页收录行后，先用它筛出「本页存在精选的话题」，只对这批话题做一遍精选表查询（04 的 1）；没有它就得逐话题各查一次。

**索引**：

```sql
CREATE INDEX index_collection_topics_on_topic_id_and_collection_id
    ON collection_topics USING btree (topic_id, collection_id)

CREATE INDEX index_collection_topics_on_collection_id_and_created_at
    ON collection_topics USING btree (collection_id, created_at, topic_id)
```

两条索引分别对应上面两条高频查询：前者服务「话题 → 专辑」的反查，后者服务「专辑 → 话题」的列表与翻页。后者把 `topic_id` 并进键尾：阅读页按 `created_at` 与 `topic_id` 同向排序，键里带上它之后两个方向都整条命中，`created_at` 相同的两行之间也有确定次序，翻页不会重复或漏行。

## 3. `collection_teamworkers`

```sql
CREATE TABLE collection_teamworkers (
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  is_owner BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (collection_id, user_id)
)
```

**表用途**：专辑的团队行——owner 与共同维护者同表，用 `is_owner` 区分。一行 = 一人对一张专辑的一个身份；两种身份互斥，故同一 `(collection_id, user_id)` 不会重复。owner **不计入**共同维护者数（03 的 1）。

**查询业务**：

- 某专辑的团队与 owner（03 的 4）：按 `collection_id` 取。

- 某用户创建或维护的专辑（03 的 3 的 `username`、04 的 6）：按 `user_id` 查。

- owner 唯一性由 DB 保证（下方部分唯一索引），不靠业务层。

- owner 删号 → 该行随 `users` 级联删除，专辑随即成「无主」（`owner` 为 null，见 09 的 4）。

**索引**：

```sql
CREATE UNIQUE INDEX uq_collection_teamworkers_on_single_owner
    ON collection_teamworkers USING btree (collection_id)
    WHERE is_owner

CREATE INDEX index_collection_teamworkers_on_collection_id
    ON collection_teamworkers USING btree (collection_id)

CREATE INDEX index_collection_teamworkers_on_user_id_and_collection_id
    ON collection_teamworkers USING btree (user_id, collection_id)
```

第一条 `WHERE is_owner` 的部分唯一索引承担「每张专辑至多一个 owner」的约束，并顺带服务「取该专辑的 owner 行」。第二条是对同一列的**整列**索引：共同维护者方向的查询谓词是 `is_owner = false`，部分索引的谓词不成立、用不上，而 owner 每辑只有一行、部分索引省不下体积——整列索引一条同时覆盖两种身份与专辑级联删除。第三条服务用户方向：`username` 过滤与 `mine` 的取 id 子查询、按人计的名额与角色判定，以及 user 级联删除。

## 4. `collection_topic_selected_replies`

```sql
CREATE TABLE collection_topic_selected_replies (
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  topic_id INTEGER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
  post_id INTEGER NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (collection_id, post_id)
)
```

**表用途**：被收录话题里的精选回复。复合主键 `(collection_id, post_id)` 保证同一帖在同一专辑至多被精选一次。收录到精选的前置关系由业务层校验（04 的 4）。

**查询业务**：

- 按 `(collection_id, topic_id)` 取某专辑某话题的全部精选（04 的 1 的内联、04 的 2 的翻页）。内联时只取 `post_id` 最小的若干条 + 1 条探针，溢出的部分由翻页端点补（04 的 1）。

- 帖子**物理销毁**由 `post_id` 的外键级联清行；帖子**软删 / 恢复不动行**，可见性只在读端按访问者过滤（04 的 1、08 的 3）。

**冗余列**：`topic_id` 是冗余快照（`post_id` 当时所属的话题），只在写时校验，**DB 不保证它始终成立**——帖子被跨话题移动（split / merge）后本行会滞留旧话题（08 的 3）。

**索引**：

```sql
CREATE INDEX index_collection_selected_replies_on_collection_topic_post
    ON collection_topic_selected_replies USING btree (collection_id, topic_id, post_id)

CREATE INDEX index_collection_topic_selected_replies_on_topic_id
    ON collection_topic_selected_replies USING btree (topic_id)

CREATE INDEX index_collection_topic_selected_replies_on_post_id
    ON collection_topic_selected_replies USING btree (post_id)
```

第一条服务按 `(collection_id, topic_id)` 取精选的两处（04 的 1 的内联、04 的 2 的翻页）：键尾带上 `post_id` 后，取窗口的查询整条命中、不再额外排序。索引名是手写缩短的——默认的 `index_<表>_on_<各列>` 形式超出 PostgreSQL 63 字符的标识符上限，会被静默截断。后两条是外键引用列的索引：话题或帖子硬删时按 `topic_id` / `post_id` 级联，而复合主键 `(collection_id, post_id)` 以 `collection_id` 打头，两个方向都覆盖不到。

## 5. `collection_subscribers`

```sql
CREATE TABLE collection_subscribers (
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (collection_id, user_id)
)
```

**表用途**：订阅行，一行 = 一人订阅一张专辑。建专辑 / 成为 owner 时**自动落一行**，故 owner 也在表里——但 owner 行不计入 `subscribers_count`（03 的 1）。

**查询业务**：

- 按 `collection_id` 找订阅者：发「专辑有新收录」通知时现算收件人（09 的 2）——主键以 `collection_id` 打头，已覆盖。

- 按 `user_id` 找该用户订阅的专辑，JOIN `collections`（04 的 6）。

- `subscribers_count` 由本表行数推导，但落成 `collections` 上的冗余列（08 的 1）。

**索引**：

```sql
CREATE INDEX index_collection_subscribers_on_user_id_and_collection_id
    ON collection_subscribers USING btree (user_id, collection_id)

CREATE INDEX index_collection_subscribers_on_collection_id_and_created_at
    ON collection_subscribers USING btree (collection_id, created_at)
```

第一条服务用户方向（04 的 6 的订阅列表与订阅判定），第二条服务订阅者列表（02 的 5）——该列表按 `created_at` 排序翻页，而主键 `(collection_id, user_id)` 排不了它。两条外键引用列分别由主键与第一条索引打头覆盖，无需另建。

## 6. `collection_invites`

```sql
CREATE TABLE collection_invites (
  id SERIAL PRIMARY KEY,
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  inviter_user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
  invitee_user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
  action_type INTEGER NOT NULL,
  accept BOOLEAN,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
)
```

**表用途**：**流程表**——一行 = 一次邀请的完整生命周期（未决 → 接受 / 拒绝 / 过期 / 被撤）。它不是关联表，故用自增代理主键而非复合主键。`action_type`：0 = 邀共同维护者、1 = 邀成新 owner；`accept`：`NULL` 未决、`true` 接受、`false` 拒绝。

**查询业务**：

- 某专辑的邀请记录，按 `created_at` 倒序 + 翻页（05 的 2.3）。

- 某用户的受邀收件箱，按 `created_at` 倒序（05 的 2.4）。

- 发起时的名额占位与各项前置校验都现查本表（05 的 2.1）；过期行的清理按 `created_at` 与 history 窗口做（05 的 2.6）。

**外键方向有意不同**：`collection_id` 是 `ON DELETE CASCADE`（专辑没了，邀请行随之清掉）；两个用户外键是 `ON DELETE SET NULL`——发起者 / 受邀人删号后**保留这条历史行**，只把对应槽位置空（审计里该槽位记 `❌`，见 10 的 1）。

**索引**：

```sql
CREATE INDEX index_collection_invites_on_collection_id_and_created_at
    ON collection_invites USING btree (collection_id, created_at)

CREATE INDEX index_collection_invites_on_invitee_user_id_and_created_at
    ON collection_invites USING btree (invitee_user_id, created_at)

CREATE INDEX index_collection_invites_on_inviter_user_id
    ON collection_invites USING btree (inviter_user_id)
```

前两条分别服务「该专辑的邀请记录」与「该用户的收件箱」，两者都按 `created_at` 排序并受保留期约束。第三条只服务外键：发起者方向没有任何查询，但 `inviter_user_id` 的 `SET NULL` 级联在用户注销时要按该列更新行，需要自己的通路。
