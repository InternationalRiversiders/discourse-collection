# 数据一致性（业务层原子维护，无 DB 触发器）

以下写入必须在**同一事务**里完成，维护方（Service）保证。

## 1. 计数与时间列

- `collections.topic_count` / `last_topic_added_at`：随「收录 / 移除」增减与重算（04 的 3 / 04 的 5）。

- `collections.updated_at`：任何内容 / 元信息变更置 now（仅收录内容变更加 `last_topic_added_at`）。

- `collections.subscribers_count`（存储列）：订阅写入方维护——非 owner 订阅行增删时 ±1；凡改变 owner 或 owner 订阅行的写（建专辑 03 的 2、**换主邀请接受** 05 的 2.5 `type=1`）在事务后**按规则重算**（= 订阅行数 − 当前 owner 行，见 02 的 5）。owner 订阅行**不计入**，故其增减、owner 删号级联删行都不改计数。

## 2. 收录行、团队行与流程行

- `collection_topics.has_selected_reply`：随精选 / 取消精选与移除收录置位（04 的 4 / 04 的 5）。

- `collection_teamworkers.is_owner` 的写入全部收在两条业务路径：建专辑 03 的 2（owner 行落 + owner 订阅行）与**换主邀请接受** 05 的 2.5 `type=1`（新主置行 + 旧主恒 demote + 订阅计数重算）——加维护者（`type=0` 接受）只插 `is_owner=false` 行，不触 owner 语义。

- `collection_invites`（流程表）：邀请为「流程状态」，**发起不 bump** 专辑 `updated_at`、不占团队行；占位与释放规则见 05 的 2.1 / 2.5——`type=0` 名额在发起时占位（现有行 + 有效未决计），接受 / 拒绝 / 撤销 / 过期释放；`type=1` 每辑同时至多一条有效未决。行生命周期由两道时间闸控制（validity / history，见 05 的 2.6），历史行不挡重邀。

## 3. 级联清理与软删

- 删除专辑由 FK `ON DELETE CASCADE` 清空收录与精选与邀请行（专辑删除自然清其 invite）；无触发器兜底。**通知行不在此列**——它在核心表上，本插件无外键可达，由删除**提交后**入队的 job 异步清（09 的 4）。

- `collection_topic_selected_replies` 行**不随帖子软删 / 可见性变化自动清理**（无触发器、写端不维护）——精选是「选择记录」，不代表帖子当前可见：软删 / recover 都**不动**行，读端（04 的 1）按访问者 `can_see_post?` 现态过滤，帖子恢复后精选自动复原；仅帖子**物理销毁**由 FK `post_id REFERENCES posts(id) ON DELETE CASCADE` 级联清行。**显式取消精选**（04 的 4 的 `remove`）随时可删行——软删后仍可撤销（`remove` 只按行删、不复查 post 存活），删掉即解除、帖子恢复后不再复原。

- `collection_topic_selected_replies.topic_id` 是**冗余**（`post_id` 处所属话题的快照），归属只在**写时校验**（04 的 4 要求 post 属该 topic、04 的 5 移除收录时清该 `(collection, topic)` 的全部精选行）；**DB 无约束保证「精选行 post 当前属于该 topic」**。若 core 端把被精选的 post **跨话题移动**（split / merge），精选行 `topic_id` 滞留旧话题 → 阅读页会把已移走的回复仍当该话题的精选展示；topic / post 不物理删则 FK CASCADE 不触发。**已知限制、低频编辑可接受**：不做迁移 / 补偿清理，写端后续发帖移动时若需精确可由写侧重写行（暂无此写端点）。
